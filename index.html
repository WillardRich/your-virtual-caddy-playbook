02

IDE selection and setup

Standard IDE: Cursor — AI-assisted code editor with a VS Code-style workflow. GitHub is the source of truth; Lovable may be used for early UI iteration, but changes must be reviewed in the repository.

Download Cursor · Install Git · Install Node.js LTS

  1. Install Cursor, Git, and the current Node.js LTS release.
  2. Accept the GitHub repository invitation and sign in to GitHub in your browser.
  3. Clone the repository from GitHub (Code → HTTPS → copy URL), then in a terminal run:
git clone <YOUR_GITHUB_REPOSITORY_URL>
cd <repository-folder>
npm install
npm run dev
  1. Open the folder in Cursor. In package.json, inspect scripts and use the actual development command if it is not npm run dev.
  2. Create a local .env file only if the project’s README or environment example requires it. Ask the project owner for the correct development Supabase URL and anon/publishable key. Never copy production service-role keys to a laptop.
  3. Open the local URL printed by the dev server, commonly http://localhost:5173.

Success check: the app loads locally, browser console has no new errors, and you can explain which files power the page you changed.

03

Development strategy

Workflow: lightweight Kanban. It fits a small MVP because work can move continuously without waiting for a formal sprint boundary.

  • Backlog: ideas and bugs not ready to start.
  • Ready: small, clearly described work with acceptance criteria.
  • In progress: one owner actively working on it. Keep work-in-progress low; finish before starting another task.
  • In review: pull request is open and checks/review are pending.
  • Done: acceptance criteria met, checks pass, reviewed change merged, and deployment verified when applicable.

Daily routine

  1. Pick the highest-priority ready issue; confirm scope and acceptance criteria.
  2. Post a brief update when blocked or when the plan changes.
  3. Open a pull request early for feedback; link it to the issue.
  4. Review teammates' changes, run checks, and update the board when work moves.

Keep tasks small enough to review in one sitting. Every issue should describe the user impact, expected behavior, and a way to verify completion.

04

Git strategy and controls

Source of truth: GitHub. Use short-lived feature branches; do not work directly on the protected default branch.

git switch main
git pull
git switch -c feat/123-shot-advice-copy
# make and test changes
git add .
git commit -m "feat(advice): clarify shot recommendation"
git push -u origin feat/123-shot-advice-copy

Branch and commit conventions

  • Branch names: feat/123-short-description, fix/124-short-description, docs/125-short-description.
  • Commit format: type(scope): imperative summary. Types: feat, fix, docs, test, refactor, chore.
  • One logical change per pull request. Link the issue and include what changed, how it was tested, screenshots for UI changes, and any migration/config impact.

Review controls

Required baseline to configure in GitHub: protect main; require pull requests; require at least one approval when a second reviewer is available; require CI checks; dismiss stale approvals after new commits; block force pushes and branch deletion. For a solo/student project, document when a second reviewer is unavailable rather than claiming approvals are enforced.

06

AI agents and controls

Approved workflow: Cursor AI for code explanation, scaffolding, refactoring suggestions, and tests; Lovable for rapid UI prototypes when appropriate. GitHub remains the source of truth. Treat generated output as an untrusted contribution, not as approved code.

  • Never paste production secrets, service-role keys, private customer data, or confidential credentials into an AI prompt.
  • Give the agent a narrow task and explicit constraints; inspect every changed file and the full diff.
  • Do not accept generated SQL/RLS policies, authentication logic, authorization checks, or dependency changes without manually validating them.
  • Run lint, tests, and a security review after AI-assisted changes. The developer who commits the change is responsible for it.
  • Do not let an agent deploy to production, rotate credentials, delete data, or run destructive commands without explicit human review.
  • Do not treat AI-generated citations, API behavior, or golf/course recommendations as verified facts; validate against trusted sources and product requirements.

08

Testing frameworks

Proposed baseline for a TypeScript web app: Vitest for unit/component-adjacent tests and React Testing Library if the UI uses React. Use Playwright for a small set of browser-level smoke tests once the core flows stabilize. Verify the actual framework in the repo before installing anything.

  • Unit tests: distance/club selection logic, input validation, formatting, and other pure functions.
  • Component tests: required inputs, loading/error states, and readable advice output.
  • Integration checks: sign-up/login, profile read/write, and Supabase RLS behavior using a development project and test account.
  • Smoke test: app loads; user can sign in; onboarding/profile saves; advice form validates inputs and renders a result.

09

Other controls, tools, and procedures

Supabase: authentication and database

Supabase is used for authentication and PostgreSQL data. The project has a profiles table keyed to the authenticated user, with profile fields and an onboarding-completed flag; row-level security policies should restrict users to their own rows.

  1. Get access to the team's Supabase project from the owner; use development credentials locally.
  2. Apply schema changes through reviewed SQL migration files, not undocumented dashboard-only edits.
  3. Enable RLS on tables containing user data. Policies must scope reads/writes to the authenticated user, typically by comparing the row's user ID to auth.uid().
  4. Test authorization as two different users: one user must not read or modify the other's profile.

Supabase dashboard · RLS guide · Auth guide

Secrets and environment configuration

  • Keep local environment files out of Git; ensure .env is in .gitignore.
  • Commit a .env.example containing variable names only, never values.
  • Browser-exposed Supabase anon/publishable keys are not a substitute for RLS. Never expose the service-role key in frontend code.
  • If a secret is committed or pasted publicly, treat it as compromised: tell the project owner, rotate it, and remove it from active use.

Deployment and release

  1. Merge only after review and checks pass.
  2. Deploy through the configured hosting provider's connected GitHub workflow; confirm the actual provider and production URL with the project owner.
  3. For database changes, back up or otherwise protect important data, review migration order, and verify RLS after deployment.
  4. Run the smoke-test checklist against the deployed version and check logs for errors.
  5. If a release breaks the app, revert the code change or roll back using the hosting/database provider's supported process; communicate the issue and avoid unreviewed emergency edits.

Support and incident handling

This MVP does not yet have a formal on-call rotation documented. For a production issue, capture the time, affected flow, error message, and steps to reproduce; notify the project owner. Do not share user information or secrets in public tickets. Prioritize authentication failures, data exposure, and data loss above cosmetic bugs.
